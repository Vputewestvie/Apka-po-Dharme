## 1. Участники: основные выводы

### 🛡️ Офицер безопасности

- **Главное**：проект был уязвим для полной подмены пользователя. Заголовок `x-user-id` принимался без проверки окружения — любой клиент в production мог назваться любым пользователем, передав один заголовок.
- **Второе по значимости**：IDOR. Из 22 записывающих эндпоинтов только 4 GET-обработчика использовали `requiredUserId()`; остальные брали `userId` из тела запроса. Проверено живьём: до правки Боб переименовал практику Алисы и получил HTTP 200.
- **Скрытая поломка**：бот не отправлял вообще никаких заголовков авторизации, поэтому все его вызовы API падали с 401 — уведомления были мертвы, но это было незаметно, потому что бот и так не запускался без токена.

### ✅ QA-лид

- Выдал вердикт **NO-GO** на основании двух «битых» зависимостей. **Вердикт ошибочен**, опровергнут проверкой содержимого tarball'ов (`npm pack` + `tar -tzf`): все файлы на месте. Корень — шим safe-delete в среде исполнения, обрывающий распаковку npm на середине. После переустановки с отключённым шимом оба «блокера» исчезли **без единой правки в коде**.
- **Урок**：прежде чем пинить версии зависимостей, нужно сверить содержимое tarball'а с тем, что реально легло в `node_modules`. Предлагавшийся даунгрейд zod до v3 вдобавок сломал бы код — в проекте используется синтаксис v4 (`z.record(z.string(), z.string())`).

### 🔧 Исполнитель правок

- Написал 13 регрессионных тестов по авторизации, закрывающих найденные дыры. Затем завис (доработка не была применена) — оставшиеся правки выполнены главным инженером.

### 👤 Главный инженер

- Разобрал 4 расхождения E2E: **два оказались реальными багами, два —artifact'ами теста**. Главный — `/timer/add-time` был полностью нерабочим: Zod-схема не объявляла `minutes`/`seconds`, Zod отбрасывает неизвестные ключи, сервис получал 0, домен требовал `> 0` → 500. Кнопка «+5 минут» не работала изначально.
- Нашёл **скрытую ловушку локального запуска**：`VITE_DEV_USER_ID` нигде не задан, а Vite читает `.env` только из `apps/mini-app/` (в отличие от API, у которого собственный загрузчик, поднимающийся вверх по каталогам). Без этой переменной приложение в браузере **молча показывало демо-данные** и не сохраняло созданные практики — это легко принять за «проект не работает».

## 🚀 Как запускать

**Способ 1 — скрипт (рекомендуется)**：двойной щелчок по `start-local.cmd`. Откроются два окна (API и Mini App), интерфейс — на http://localhost:5173. Остановка — `stop-local.cmd` или просто закрыть оба окна.

**Способ 2 — вручную** из `C:\Proekti\Mini apka dlya po dharme`：

```bash
# терминал 1
npm run dev:api        # http://localhost:3001

# терминал 2
npm run dev:mini-app   # http://localhost:5173
```

**Проверить всё разом**：`bash e2e-check.sh` — 31 проверка, сам поднимает и гасит API.

> ⚠️ Если команды npm/node падают с жалобами на отсутствующие файлы внутри `node_modules` — перед запуском выполните `unset NODE_OPTIONS && export CODEBUDDY_SAFE_DELETE_ENABLED=0`. Это особенность среды, не проекта.

## ⚠️ Известные ограничения

- **База данных** — файл SQLite по пути `apps/data/app.sqlite`. Данные локального пользователя сохраняются между запусками; удалить файл = начать с нуля.
- **AI-функции** (расписание по тексту/голосу) работают на `MockAiProvider` — ключей в `.env` нет.
- **Бот** не запускается без `TELEGRAM_BOT_TOKEN`. Это не мешает API и Mini App.
- **Материалы** принимаются только с белого списка доменов (`advayta.org`, `institute-vasishtha.com`, `sanatanadharma.world`) — так задумано.
- **E2E-прогон** оставляет тестовые данные (пользователи `alice-*`, `bob-*`) в локальной базе. Для чистого старта удалите файлы `data/*.sqlite*`.
